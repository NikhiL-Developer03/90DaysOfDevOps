## 1. Multi-Job Workflow

A workflow can contain multiple jobs. By default, independent jobs can run in parallel.

Sometimes, we need one job to wait for another job to finish successfully. We use `needs` to create job dependencies.

### Practical: Create a Multi-Job Workflow

File: `.github/workflows/multi-job.yml`

```yaml
name: Multi Job Workflow

on:
  push:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Build application
        run: echo "Building the app"

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Run tests
        run: echo "Running tests"

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: Deploy application
        run: echo "Deploying"
```

### Workflow Execution

```text
BUILD
  |
  v
TEST
  |
  v
DEPLOY
```

### What is `needs`?

- `needs: build` means the test job waits for the build job.
- `needs: test` means the deploy job waits for the test job.
- If a required job fails, dependent jobs are skipped by default.

**In simple words:** `needs` controls the order in which jobs execute.

## 2. Environment Variables

Environment variables store values that can be used by workflow jobs and steps.

GitHub Actions supports environment variables at three levels.

### A. Workflow-Level Variables

Available to all jobs and steps in the workflow.

```yaml
env:
  APP_NAME: myapp
```

### B. Job-Level Variables

Available only inside the job where they are defined.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    env:
      ENVIRONMENT: staging
```

### C. Step-Level Variables

Available only inside the particular step.

```yaml
steps:
  - name: Print version
    env:
      VERSION: 1.0.0
    run: echo "$VERSION"
```

### Practical: Environment Variables Workflow

File: `.github/workflows/env-vars.yml`

```yaml
name: Environment Variables Demo

on:
  push:

env:
  APP_NAME: myapp

jobs:
  show-variables:
    runs-on: ubuntu-latest

    env:
      ENVIRONMENT: staging

    steps:
      - name: Print environment variables
        env:
          VERSION: 1.0.0
        run: |
          echo "App Name: $APP_NAME"
          echo "Environment: $ENVIRONMENT"
          echo "Version: $VERSION"
          echo "Commit SHA: ${{ github.sha }}"
          echo "Triggered by: ${{ github.actor }}"
```

### GitHub Context Variables

GitHub provides built-in context variables that give information about workflow runs.

| Variable | Purpose |
|---|---|
| `${{ github.sha }}` | Commit SHA that triggered the workflow |
| `${{ github.actor }}` | GitHub username that triggered the workflow |
| `${{ github.ref }}` | Branch or tag reference |
| `${{ github.event_name }}` | Event that triggered the workflow |

### Practical Output

| Variable | Value |
|---|---|
| APP_NAME | myapp |
| ENVIRONMENT | staging |
| VERSION | 1.0.0 |
| github.sha | Commit SHA |
| github.actor | GitHub username |

**Important:** Step-level variables cannot be accessed directly by other steps or jobs. Their scope is limited to that step.

## 3. Job Outputs

Sometimes one job generates information that another job needs.

For this, GitHub Actions provides **job outputs**.

### Practical: Pass Today's Date Between Jobs

File: `.github/workflows/job-outputs.yml`

```yaml
name: Job Outputs Demo

on:
  push:

jobs:
  generate:
    runs-on: ubuntu-latest

    outputs:
      today: ${{ steps.date.outputs.today }}

    steps:
      - name: Generate today's date
        id: date
        run: echo "today=$(date +%Y-%m-%d)" >> "$GITHUB_OUTPUT"

  display:
    needs: generate
    runs-on: ubuntu-latest

    steps:
      - name: Print generated date
        run: 'echo "Date received from generate job: ${{ needs.generate.outputs.today }}"'
```

### Understand the Important Parts

**Step 1: Generate an output**

```bash
echo "today=$(date +%Y-%m-%d)" >> "$GITHUB_OUTPUT"
```

This creates a step output named `today`.

**Step 2: Expose the step output at job level**

```yaml
outputs:
  today: ${{ steps.date.outputs.today }}
```

This makes the value available to other dependent jobs.

**Step 3: Read the output from another job**

```yaml
needs: generate
```

```yaml
${{ needs.generate.outputs.today }}
```

This retrieves the date generated by the `generate` job.

### Workflow Execution

```text
GENERATE JOB
     |
     | Creates today's date
     |
     v
 JOB OUTPUT: today
     |
     v
 DISPLAY JOB
     |
     v
 Prints received date
```

### Why Do We Pass Outputs Between Jobs?

- Jobs run in separate execution environments.
- One job may generate information needed by another job.
- Outputs allow jobs to share generated values.
- Useful for passing build versions, dates, IDs, and other information.

**In simple words:** Job outputs help us transfer data between dependent jobs.

## 4. Conditionals

Conditionals control whether a particular step or job should execute.

GitHub Actions uses the `if` condition to control execution.

### A. Run Only on Main Branch

```yaml
- name: Run only on main
  if: github.ref == 'refs/heads/main'
  run: echo "Running on main branch"
```

This step runs only when the workflow is running on the `main` branch.

### B. Run After a Previous Step Fails

```yaml
- name: Run after failure
  if: failure()
  run: echo "A previous step failed"
```

`failure()` checks whether a previous step or job has failed.

### C. Run Only on Push Events

```yaml
on:
  push:
```

This workflow trigger runs on push events, not pull request events.

A job can also use:

```yaml
if: github.event_name == 'push'
```

### D. Continue on Error

```yaml
- name: Intentional failure
  continue-on-error: true
  run: exit 1
```

`continue-on-error: true` allows the workflow to continue even if that step fails.

### Practical: Conditionals Workflow

File: `.github/workflows/conditionals.yml`

```yaml
name: Conditionals Demo

on:
  push:

jobs:
  conditional-job:
    runs-on: ubuntu-latest

    steps:
      - name: Normal step
        run: echo "This step runs normally"

      - name: Run only on main
        if: github.ref == 'refs/heads/main'
        run: echo "Running on main branch"

      - name: Intentional failure
        id: test-failure
        continue-on-error: true
        run: exit 1

      - name: Run after failure
        if: steps.test-failure.outcome == 'failure'
        run: echo "The previous step failed"

  push-only-job:
    if: github.event_name == 'push'
    runs-on: ubuntu-latest

    steps:
      - name: Push event check
        run: echo "This job runs only for push events"
```

### Important Difference

| Concept | Meaning |
|---|---|
| `failure()` | Checks whether a previous step or job failed |
| `continue-on-error: true` | Allows execution to continue after a step fails |
| `steps.test-failure.outcome` | Checks the actual outcome of a particular step |

## 5. Smart Pipeline

In this task, I combined multiple concepts into one workflow.

The workflow contains:

- A lint job.
- A test job.
- A summary job.

The lint and test jobs run independently and can execute in parallel.

The summary job waits for both jobs to succeed.

### Practical: Smart Pipeline

File: `.github/workflows/smart-pipeline.yml`

```yaml
name: Smart Pipeline

on:
  push:

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - name: Lint check
        run: echo "Running lint checks"

  test:
    runs-on: ubuntu-latest
    steps:
      - name: Test application
        run: echo "Running application tests"

  summary:
    needs: [lint, test]
    runs-on: ubuntu-latest
    steps:
      - name: Show branch type
        run: |
          if [ "${GITHUB_REF}" = "refs/heads/main" ]; then
            echo "This is a main branch push"
          else
            echo "This is a feature branch push"
          fi

      - name: Show commit message
        run: 'echo "Commit message: ${{ github.event.head_commit.message }}"'
```

### Workflow Execution

```text
       LINT          TEST
         |             |
         |             |
         +------+------+
                |
                v
             SUMMARY
                |
        +-------+-------+
        |               |
    Branch type    Commit message
```

### Important Concepts

**1. Parallel Jobs**

Lint and test have no dependencies, so GitHub can execute them in parallel.

**2. Multiple Dependencies**

```yaml
needs: [lint, test]
```

The summary job waits for both lint and test to succeed.

**3. Branch Detection**

```bash
if [ "${GITHUB_REF}" = "refs/heads/main" ]; then
```

Checks whether the current branch is `main` or a feature branch.

**4. Commit Message**

```yaml
${{ github.event.head_commit.message }}
```

Gets the latest commit message from the push event.

## 6. Important GitHub Actions Concepts – Quick Revision

| Concept | Purpose |
|---|---|
| `jobs` | Defines jobs in a workflow |
| `steps` | Defines individual tasks inside a job |
| `needs` | Creates dependencies between jobs |
| `env` | Defines environment variables |
| `$GITHUB_OUTPUT` | Saves step outputs |
| `outputs` | Exposes values from a job |
| `if` | Controls conditional execution |
| `failure()` | Checks for a previous failure |

## 8. Key Learnings

1. Multiple jobs can run independently or depend on other jobs.
2. `needs` controls job execution order.
3. Environment variables can be defined at workflow, job, and step levels.
4. Job outputs allow us to pass generated data between jobs.
5. Conditions control when jobs and steps execute.
6. `continue-on-error` allows a workflow to continue after an error.
7. Smart pipelines combine parallel execution, dependencies, and conditional logic.
