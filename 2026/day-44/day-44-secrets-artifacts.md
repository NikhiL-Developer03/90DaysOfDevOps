## Task 1 – GitHub Secrets

### What are GitHub Secrets?

GitHub Secrets are encrypted values used to store sensitive information such as passwords, API keys, access tokens, and credentials.

Instead of hardcoding sensitive information inside workflow files, we store it in GitHub repository settings.

### Steps performed

1. Opened repository Settings.
2. Navigated to Secrets and variables → Actions.
3. Created a repository secret named `MY_SECRET_MESSAGE`.
4. Created a workflow to check whether the secret is available.

### Workflow: `secrets-demo.yml`

```yaml
name: GitHub Secrets Demo

on:
  push:

jobs:
  check-secret:
    runs-on: ubuntu-latest

    steps:
      - name: Check if secret exists
        env:
          MY_SECRET: ${{ secrets.MY_SECRET_MESSAGE }}
        run: |
          if [ -n "$MY_SECRET" ]; then
            echo "The secret is set: true"
          else
            echo "The secret is set: false"
            exit 1
          fi
```

### Important concepts

- `${{ secrets.MY_SECRET_MESSAGE }}` retrieves a repository secret.
- `env` passes the secret to the step as an environment variable.
- `$MY_SECRET` accesses the variable in the shell.
- `[ -n "$MY_SECRET" ]` checks whether the variable is non-empty.

**Expected output:**

```text
The secret is set: true
```

### Why should we never print secrets in CI logs?

- Logs may be accessible to people with repository access.
- Credentials could be exposed accidentally.
- Exposed tokens or passwords can allow unauthorized access.
- Logs may be retained or copied into other systems.

GitHub automatically masks registered secret values in many log situations, usually displaying `***`. However, masking is not guaranteed protection. Secrets should never be deliberately printed.

**Important:** Directly printing the secret value was not performed during this practice.

## Task 2 – Use Secrets as Environment Variables

Secrets can be passed to individual workflow steps using environment variables.

Example:

```yaml
- name: Use secret safely
  env:
    MY_SECRET: ${{ secrets.MY_SECRET_MESSAGE }}
  run: |
    if [ -n "$MY_SECRET" ]; then
      echo "Secret is available"
    fi
```

## Task 3 – Upload Artifacts

### What are artifacts?

Artifacts are files generated during a workflow that can be saved and downloaded after the workflow finishes.

Examples:

- Test reports
- Application build files
- Log files
- ZIP packages

### Workflow: `artifacts.yml`

```yaml
name: Upload Artifacts Demo

on:
  push:

jobs:
  generate-report:
    runs-on: ubuntu-latest

    steps:
      - name: Create report directory
        run: mkdir -p reports

      - name: Generate test report
        run: |
          echo "CI Test Report" > reports/test-report.txt
          echo "Status: PASSED" >> reports/test-report.txt
          echo "Generated by GitHub Actions" >> reports/test-report.txt

      - name: Display report
        run: cat reports/test-report.txt

      - name: Upload test report
        uses: actions/upload-artifact@v4
        with:
          name: test-report
          path: reports/test-report.txt
```

### Important concepts

- `mkdir -p reports` creates the report directory.
- `echo` generates the report file.
- `actions/upload-artifact@v4` uploads the file.
- `name` specifies the artifact name.
- `path` specifies which file should be uploaded.

### Verification

Successfully downloaded and opened `test-report` from the GitHub Actions Summary page.

**Downloaded report:**

```text
CI Test Report
Status: PASSED
Generated by GitHub Actions
```

**Result:** Artifact upload and download successful.

## Task 4 – Download Artifacts Between Jobs

### Why do we need artifacts between jobs?

GitHub-hosted jobs generally run on separate runner machines. Files created in one job are not automatically available in another job.

Artifacts allow us to transfer files between jobs.

### Workflow: `artifacts-between-jobs.yml`

```yaml
name: Artifacts Between Jobs

on:
  push:

jobs:
  generate:
    runs-on: ubuntu-latest

    steps:
      - name: Generate report
        run: |
          echo "Report generated by Job 1" > report.txt
          echo "Status: SUCCESS" >> report.txt

      - name: Upload report
        uses: actions/upload-artifact@v4
        with:
          name: job-report
          path: report.txt

  consume:
    needs: generate
    runs-on: ubuntu-latest

    steps:
      - name: Download report
        uses: actions/download-artifact@v4
        with:
          name: job-report

      - name: Read report
        run: cat report.txt
```

### Important concepts

**1. Upload artifact**

```yaml
uses: actions/upload-artifact@v4
```

Uploads the generated report.

**2. Job dependency**

```yaml
needs: generate
```

Makes the `consume` job wait until the `generate` job succeeds.

**3. Download artifact**

```yaml
uses: actions/download-artifact@v4
```

Downloads the artifact created by the previous job.

### Expected output

```text
Report generated by Job 1
Status: SUCCESS
```

### When would we use artifacts in a real pipeline?

For example, when building and deploying an application:

1. Build job generates an application package.
2. Build job uploads the package as an artifact.
3. Test job downloads and tests the package.
4. Deploy job downloads the approved package and deploys it.

**Result:** Both jobs completed successfully, and the artifact was transferred between them.

## Task 5 – Run Real Tests in CI

### What is CI testing?

Continuous Integration (CI) automatically runs tests whenever code changes are pushed to a repository.

If a test fails and returns a non-zero exit code, GitHub Actions marks the workflow as failed.

### Step 1: Create a Python test script

File: `tests/test_calculator.py`

```python
def add(a, b):
    return a + b


def test_add():
    assert add(10, 20) == 30
    print("Addition test passed!")


def test_add_negative():
    assert add(-5, 5) == 0
    print("Negative number test passed!")


if __name__ == "__main__":
    test_add()
    test_add_negative()
    print("All tests passed!")
```

### Step 2: Run the script locally

Command:

```bash
python3 tests/test_calculator.py
```

Output:

```text
Addition test passed!
Negative number test passed!
All tests passed!
```

### Step 3: Create GitHub Actions workflow

File: `.github/workflows/python-tests.yml`

```yaml
name: Python Tests CI

on:
  push:

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Run Python tests
        run: python tests/test_calculator.py
```

### Important concepts

- `actions/checkout@v4` downloads repository code onto the runner.
- `actions/setup-python@v5` sets up Python.
- `python tests/test_calculator.py` executes the test script.
- A failed assertion causes Python to exit with a non-zero status code, which fails the workflow step.

No additional dependencies were required because the script uses Python's built-in features.

### Step 4: Verify CI execution

Successfully pushed the Python script and workflow.

GitHub Actions output:

```text
Addition test passed!
Negative number test passed!
All tests passed!
```

**Result:** The first real Python test run passed successfully in GitHub Actions.

## Task 6 – Caching

### What is caching?

Caching stores reusable files, such as downloaded dependencies, so later workflow runs can avoid downloading them again.

This can reduce workflow execution time.

### Example: Cache Python dependencies

```yaml
- name: Set up Python
  uses: actions/setup-python@v5
  with:
    python-version: "3.12"

- name: Cache pip dependencies
  uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}
    restore-keys: |
      ${{ runner.os }}-pip-

- name: Install dependencies
  run: pip install -r requirements.txt
```

### Important concepts

- `actions/cache@v4` saves and restores cached files.
- `path` specifies what should be cached.
- `key` identifies a particular cache.
- `hashFiles()` generates a hash based on dependency files.
- `restore-keys` provides fallback cache keys.

### What is being cached and where is it stored?

In this example, the pip download/cache directory (`~/.cache/pip`) is cached.

GitHub Actions stores the cache remotely and restores it to the runner when a matching cache is available. It is not simply stored permanently on the runner machine.
